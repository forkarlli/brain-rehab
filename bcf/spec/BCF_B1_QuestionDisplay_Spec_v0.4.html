§1 目的與範圍邊界

B1 只做一件事：把凍結題庫的題幹「顯示」出來。最小、可插拔、零 rework。SA 已 PASS 此 phase boundary。

IN · B1 做
  • 讀取凍結 QB JSON（單一資料來源）
  • 依 6 domain 分組、渲染全部 48 題題幹
  • 唯讀顯示，不可作答
  • 每題產生一個 inert、病人不可見的作答插座給 B2
  • 載入時原始位元 + 結構完整性自檢（見 §3、§7）
OUT · 明確延後
  • 作答輸入元件 → B2
  • 任何 response_format 處理
  • 答案儲存 / 送 server
  • 強度、gate／modulate、任何臨床判讀
  • 依臨床 metadata 改變渲染（見 INV-02）
  • 併入 app.js／server.js、commit

§3 架構不變量（Invariants）

SA 要求把 B1 的邊界從「規則」升級為「不變量」——這三條任何實作都不得違反。

B1-INV-01RAW-BYTE IDENTITY

SHA-256 與 byte length 必須驗「載入的原始位元」，且在 parse 之前完成。

禁止 JSON.parse → JSON.stringify → SHA-256——空白、key 順序、換行都會改變結果，驗到的是「語意重建 JSON」，不是 frozen artifact bytes。

固定順序：fetch/read raw bytes → byte-length check → SHA-256 check → PASS → UTF-8 decode + parse → structural checks → render
任一步 FAIL ⇒ render = 0 questions

實作註：用 response.arrayBuffer()（非 .json()），對 ArrayBuffer 做 crypto.subtle.digest，再 TextDecoder → JSON.parse。

［§11 已定案 · Option A］ B1 只走 production／localhost（secure context），crypto.subtle 全程可用，INV-01 位元 hash 一律執行；file:// 快照路徑已移除。
B1-INV-02NO CLINICAL SEMANTIC DERIVATION

渲染行為不得依 item_class、is_phenotype、label_en、Core-24 membership、定位 metadata 或 administration parameters 而分歧。

對 B1 而言，LOCALIZING／NON_LOCALIZING_PHENOTYPE／IMPACT 都只是題目。不得因某題是 phenotype 就畫不同樣式、不同排序、或條件顯示。否則 B1 會偷偷變成 clinical logic layer。

明文條款（折入 Gemini R2／R3）：

  • 禁止 hardcode 特例：不得出現 if (item_id === 'QB-L3-…') {…} 這類依身份的分支。所有渲染一律 schema 驅動。
  • 禁止輸入端加工（B2-forward）：任何層都不得攔截、格式化、關鍵字 highlight 或自動修正使用者輸入——那也是 clinical derivation。B1 本身無輸入面，此條為 B2 綁定前置。
B1-INV-03ALL-OR-NOTHING RENDER

完整 artifact 通過身份（INV-01）與結構驗證前，任何題卡都不得進入病人可見 DOM。

先驗證完整資料集，再 construct／render。禁止逐題 render → 第 N 題才發現錯 → 清 DOM 這種做法。

§4 渲染規則

  • domain 顯示順序（B1 presentation contract 固定）：VESTIBULAR → OCULOMOTOR → CEREBELLAR → COGNITIVE → BRAINSTEM_AUTONOMIC → DAILY_FUNCTION。渲染器不得推論或產生另一套排序規則。 （已刪：若 JSON 另有排序宣告以 JSON 為準）　未來若 QB 正式新增 canonical display-order 欄位，再修本 contract，不預測 schema。
  • 題目排序：每個 domain 內保留 QB 陣列原順序（stable partition）。陣列順序＝QB authority；domain 顯示順序＝B1 presentation concern。
  • 每題顯示（病人視圖）：只顯示 patient_wording_zh。item_id 存入 DOM 的 data-item-id 供追溯，不顯示給病人（clinician/debug view 可顯示）。
  • 中性分段：病人看到 6 個中性段落「第一部分～第六部分」，不顯示臨床 domain 名稱（見 §8 D2 / SA Risk 1）。
  • 零捏造：畫面上每個病人可見的字都能對回一個 data-item-id；不渲染 QB 裡不存在的內容。

§5 作答區合約（給 B2 的插座）

  • 每題產生一個穩定、inert、病人不可見的作答插座：<div data-bcf-slot="answer" data-item-id="…"></div>（空、無控制項）。
  • B1 patient view 不顯示任何作答控制項，也不顯示任何 B2 技術提示文字。
  • debug／dev view 可顯示 slot 邊界——但那不是病人介面。
  • B2 以 data-bcf-slot 為目標注入作答元件；B1 題目 renderer 不需改動。這正是「AP-Q15／Q22／Q25 改變作答契約時只需換 B2」的接縫。
Scope 澄清（回應 Gemini「Present & Collect」用語）本 spec 的 B1 = Present only；Collect（收集作答）自 B2 起。故 Gemini 對 free-text 攔截（R2）與必填防呆（R5b）的意見原則正確、但作用在 B2——已記為 B2 綁定前置，精神折入 INV-02。B1 無任何輸入面，不做必填判斷。

§7 完整性、防禦與錯誤處理

  • 載入驗證順序：嚴格照 INV-01（raw bytes → length → SHA-256 → parse → 結構）。
  • 結構檢查：題數＝48、6 domain 各 8、class 分布＝36／4／8——一律執行。位元 hash 亦一律執行（B1 只跑 secure context，見 §11）。
  • 渲染策略：INV-03 全有全無——驗證完整資料集後才 render，不做 partial render。
  • 載入失敗態涵蓋網路／cold-start（折入 Gemini R4）：除 hash／結構失敗外，fetch 逾時、斷線、Railway 冷啟白畫面也走同一個 patient-safe error state；載入中顯示中性 loading 態，避免病人焦慮。臨床上「載不到」優於「顯示過期快取」，此為 fail-safe。〔營運註：Railway cold-start 建議以 keep-warm 或健康檢查緩解，屬 ops 不屬 B1 code。〕

§9 驗收標準

  • 準確渲染 48 題；6 domain 各 8；class 分布 36／4／8 驗證通過。
  • SHA-256 + byte-length 依 INV-01 順序驗原始位元（secure context）；結構檢查一律執行。
  • 全有全無：任何時刻都不出現 partial／invalid DOM（INV-03）。
  • 病人視圖只有題幹——無 item_id、無臨床 metadata、無作答控制項、無 B2 技術文字。
  • 畫面每段題幹都能對回 DOM 的 data-item-id。
  • 沒有任何渲染分歧依賴臨床 metadata（INV-02）；程式碼中無 if(item_id===…) 之類特例分支——全 schema 驅動。
  • 錯誤時病人畫面顯示安全訊息；技術細節僅進 console／clinician view；網路／cold-start 失敗也走同一 patient-safe error state。
  • 顯示符合 §12 神經友善標準（對比、字級、行距、減動）。
  • 狀態標籤為「題庫來源驗證通過／QB_SOURCE_VERIFIED」，非「完整／COMPLETE」。

§11 已定案：INV-01 vs file:// → Option A

［PM 定案 2026-08-16］選 Option A：移除 file:// 快照，B1 單一 production／localhost fetch 路徑。

背景衝突：INV-01 要求執行時驗原始位元 SHA-256；crypto.subtle 需 secure context（https／localhost），file:// 不支援。故「內嵌 JSON、iPad 雙擊開」的快照版無法滿足 INV-01。

選項內容裁決
AB1 只有 production／localhost 的 fetch 路徑，不做 file:// 快照。要 iPad 預覽就從 localhost／Railway 服務。✓ 採用 · 身份保證最強（INV-01 全程成立）
B允許快照版但標示 build-time 驗證、非 runtime。未採用 · 無 runtime 位元驗證
定案效果B1 全程於 secure context 執行 → INV-01 位元 hash 一律適用；不存在無法驗證身份的渲染路徑。iPad 預覽＝連 localhost／Railway，不用 file://。

§12 神經友善顯示標準（Neuro-inclusive）B1 MUST

［折入 Gemini R5a］受測者常伴腦霧、眼動異常（saccade／convergence）、交感高張。顯示層不友善 → 作答疲勞 → garbage-in。不違反任何 INV，但列 B1 UI 實作 MUST。

  • 對比：body 文字對比 ≥ WCAG AAA 7:1（至少 AA 4.5:1）；不使用低對比灰字。
  • 字級：題幹 ≥ 18px（iPad 建議更大）；避免過細字重。
  • 行距／留白：line-height ≥ 1.7；題與題間留足白，一次聚焦一題。
  • 版面：單欄、低視覺雜訊；同屏不塞過多同時元素。
  • 動態：尊重 prefers-reduced-motion；無自動播放、無閃爍（避免誘發）。
  • 觸控：B1 顯示層不放小型易誤觸元素；（B2 作答元件另需符合最小觸控尺寸）。
為何是硬要求這些是資料品質要求，不是美觀：對神經受測者，不良可近性直接等於不準確數據，是後續 BCF 演算法的污染源。此節不改題幹內容，不違反 INV-01／02。
